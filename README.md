# NAPAS Payment Switch Server

A high-performance, multi-threaded **ISO 8583 payment switch** built with .NET 8.0. This server acts as an intermediary between **Acquirer** institutions (ATMs, POS terminals) and **Issuer** banks, routing authorization requests, reversals, and network management messages in real time over raw TCP sockets. 

**Transaction types supported: Retail(Purchase), Balance Inquiry, Void/Reversal**

> **Disclaimer**: This is a testing/simulation environment. It is not affiliated with or endorsed by the real NAPAS (National Payment Corporation of Vietnam).

### Key Concepts

| Term | Description |
|:-----|:------------|
| **Acquirer (ACQ)** | The institution that owns the ATM or POS terminal. Sends the transaction request. |
| **Issuer (ISS)** | The cardholder's bank. Approves or declines the transaction. |
| **BIN** | Bank Identification Number — the first 6 digits of a card number, used to route to the correct Issuer. |
| **ISO 8583** | The international standard message format used for financial transactions. |
| **MTI** | Message Type Indicator — a 4-digit code (e.g., `0100` = Authorization Request, `0110` = Authorization Response). |
| **STAN** | System Trace Audit Number (DE#11). A unique 6-digit number per transaction. |
| **RRN** | Retrieval Reference Number (DE#37). Used for reconciliation. |
| **TRN** | Transaction Reference Number. Internal tracking ID generated by the switch. |
| **H2H** | Host-to-Host — persistent TCP connections between the switch and Issuer banks. |

## How It Works

### Message Flow (Authorization — `0100`/`0110`)

```
1. Acquirer connects to port **** via TCP
2. Acquirer sends ISO 8583 Authorization Request (MTI 0100)
3. Switch parses the binary message using IsoParser
4. Switch validates mandatory NAPAS data elements
5. Switch extracts card BIN (first 6 digits of DE#2 PAN)
6. Switch looks up the BIN in BINconfig.xml → finds the Issuer
7. Switch translates PIN block (DE#52) from ACQ zone key → ISS zone key
8. Switch forwards the request to the Issuer via persistent H2H connection
9. Issuer responds with Authorization Response (MTI 0110)
10. Switch translates PIN block back: ISS zone key → ACQ zone key
11. Switch validates response correlation (STAN, RRN match)
12. Switch logs the transaction to SQL Server
13. Switch sends the response back to the Acquirer
```

### Supported Message Types

| MTI | Type | Description |
|:----|:-----|:------------|
| `0100` | Authorization Request | Card payment / withdrawal request |
| `0110` | Authorization Response | Approval or decline from Issuer |
| `0400` | Reversal Request | Cancel a previous authorization |
| `0410` | Reversal Response | Confirmation of reversal |
| `0420` | Reversal Advice | Notification of automatic reversal |
| `0430` | Reversal Advice Response | Acknowledgement of advice |
| `0800` | Network Management Request | Echo test / sign-on / sign-off |
| `0810` | Network Management Response | Echo response |

### Connection Modes

The switch supports two connection modes for Issuers:

- **Passive Mode**: The Issuer connects *to* the switch. Used when an Issuer's `<Host>` and `<Port>` in `BINconfig.xml` are left **empty**, and the switch listens on a port defined in `ServerConfig.xml` (`<ISSlisteningPorts>`).
- **Active Mode**: The switch connects *to* the Issuer. Used when the Issuer's `<Host>` and `<Port>` are populated with an external IP and port in `BINconfig.xml`.

### Wire Format

Messages are framed with a **4-byte ASCII length header** followed by the ISO 8583 binary payload:

```
[4-byte ASCII length][ISO 8583 message bytes]
Example: "0068" + <68 bytes of ISO 8583 data>
```

## Configuration Guide

All configuration files live in the `Config/` directory at the project root. The server auto-discovers this folder by walking up from its base directory.

### 1. Server Ports — `ServerConfig.xml`

Defines which TCP ports the server listens on and general settings.

```xml
<ServerConfiguration>
  <!-- Ports for Issuer (bank host) connections -->
  <IssuerPorts>
    <Port>****</Port>  <!-- ACB -->
    <Port>****</Port>  <!-- PGB -->
    <Port>****</Port>  <!-- BIDV -->
  </IssuerPorts>

  <!-- Ports for Acquirer (ATM/POS) connections -->
  <AcquirerPorts>
    <Port>****</Port>  <!-- Primary ACQ port -->
  </AcquirerPorts>

  <Settings>
    <ConnectionTimeout>300000</ConnectionTimeout>  <!-- 5 min in ms -->
    <HealthCheckPort>****</HealthCheckPort>
  </Settings>

  <!-- Default values for mandatory NAPAS data elements -->
  <Defaults>
    <DefaultAcquirerId>****</DefaultAcquirerId>
    <DefaultCurrencyCode>704</DefaultCurrencyCode>  <!-- VND -->
    <!-- ... other defaults ... -->
  </Defaults>
</ServerConfiguration>
```

**How to add a new port**: Add a `<Port>XXXX</Port>` entry under `<IssuerPorts>` or `<AcquirerPorts>`.

---

### 2. Issuer / BIN Routing — `BINconfig.xml`

This is the **routing table**. Each `<Bank>` entry maps one or more card BINs to an Issuer's connection details.

```xml
<BinRoutingConfiguration>
  <Banks>
    <Bank>
      <BankCode>ACB</BankCode>           <!-- Short code (internal) -->
      <BankName>Asia Commercial Bank</BankName>
      <IssuerCode>****</IssuerCode>    <!-- NAPAS institution ID (DE#33) -->
      <IssuerName>ACB</IssuerName>
      <Host>****</Host>          <!-- Active Mode: Issuer's IP address. Passive Mode: Leave empty -->
      <Port>****</Port>                  <!-- Active Mode: Issuer's TCP port. Passive Mode: Leave empty -->
      <Timeout>30000</Timeout>           <!-- Connection timeout (ms) -->
      <Bins>
        <Bin>****</Bin>                <!-- Card BIN(s) that route here -->
      </Bins>
    </Bank>
    <!-- Add more banks... -->
  </Banks>
</BinRoutingConfiguration>
```

**How to configure an Issuer (Active vs Passive)**:
1. Add a new `<Bank>...</Bank>` block with the bank's details.
2. Add all card BINs that belong to this Issuer under `<Bins>`.
3. **For Active Mode (Switch connects TO Issuer)**: 
   - Set `<Host>` to the Issuer's IP address.
   - Set `<Port>` to the Issuer's TCP port.
4. **For Passive Mode (Issuer connects TO Switch)**: 
   - Leave `<Host>` and `<Port>` **completely empty** (e.g., `<Host></Host>`). 
   - Ensure the port they will connect to is listed in `ServerConfig.xml` under `<ISSlisteningPorts>`.

**Environment variable overrides**: You can override host/port at runtime without changing XML:
```bash
export NAPAS_BIN_HOST_ACB=*******
export NAPAS_BIN_PORT_ACB=****
```

### 3. Acquirer Registry — `ACQconfig.xml`

Maps Acquirer institution codes to their names. Used for logging and identification.

```xml
<AcquirerRoutingConfiguration>
  <Acquirers>
    <Acquirer>
      <AcquirerCode>****</AcquirerCode>
      <AcquirerID>ACB</AcquirerID>
    </Acquirer>
    <!-- Add more acquirers... -->
  </Acquirers>
</AcquirerRoutingConfiguration>
```

**How to add a new Acquirer**: Add an `<Acquirer>` block with the institution's NAPAS code and name.

### 4. Response Codes — `RCconfig.xml`

Lookup table for ISO 8583 response codes (DE#39). Used to provide human-readable descriptions in logs.

```xml
<ResponseCodeConfiguration>
  <Codes>
    <Code Code="code" Description="description"/>
    <Code Code="code" Description="description"/>
    <Code Code="code" Description="description"/>
    <Code Code="code" Description="description"/>
    <Code Code="code" Description="description"/>
    <!-- ... 40+ response codes defined ... -->
  </Codes>
</ResponseCodeConfiguration>
```

---

### 5. Database — `DBconfig.xml`

```xml
<DatabaseConfiguration>
  <ConnectionString></ConnectionString>  <!-- Use env variable instead! -->
  <EnableLogging>true</EnableLogging>
  <CommandTimeout>30</CommandTimeout>
</DatabaseConfiguration>
```

> **Important**: The connection string should be provided via the `NAPAS_DB_CONNECTION_STRING` environment variable (see [Environment Variables](#environment-variables)). Do NOT hardcode credentials in this file.

---

### 6. Field Validation — `NapasFieldsConfig.xml`

Defines validation rules for every ISO 8583 data element (field number, name, type, min/max length, whether it's mandatory for specific MTIs). The `NapasDataElementValidator` uses this file to reject malformed messages before routing.

## Database Setup

The project uses **SQL Server** (Azure SQL or SQL Server on-premises).

### 1. Create the Database

Run the schema script against your SQL Server instance:

```bash
# Using sqlcmd (local SQL Server)
sqlcmd -S **** -i Database/NapasSwitch_Full_Schema.sql

# Using Azure Data Studio or SSMS
# Open Database/NapasSwitch_Full_Schema.sql and execute
```

The script is **idempotent** — it can be run multiple times safely. It will:
- Create the `NAPASSwitch` database if it doesn't exist
- Create or migrate the following tables:

| Table | Purpose |
|:------|:--------|
| `TransactionLog` | Primary audit log for all processed transactions |
| `MessageCycle` | Tracks each leg of the message journey (FORWARDED → RECEIVED → OUTBOUND) |
| `TransactionLogArchive` | Created automatically by the archival procedure |

### 2. Stored Procedures

| Procedure | Purpose |
|:----------|:--------|
| `sp_ArchiveTransactionLog` | Moves old records (default: >90 days) from `TransactionLog` to `TransactionLogArchive` in batches |

## Getting Started

### Prerequisites

- [.NET 8.0 SDK](https://dotnet.microsoft.com/download/dotnet/8.0)
- SQL Server (local, Azure SQL, or Docker)
- Git

### Build & Run (Local)

```bash
# 1. Clone the repo
git clone https://github.com/luonglemlinh/napasswitchServer.git
cd napasswitchServer

# 2. Set up the database
# Run Database/NapasSwitch_Full_Schema.sql against your SQL Server

# 3. Set environment variables
# (Windows PowerShell)
$env:NAPAS_DB_CONNECTION_STRING = "Server=localhost;Database=NAPASSwitch;Integrated Security=true;TrustServerCertificate=true;" (or your cloud's connection string)
$env:ALLOW_HSM_STUB = "true" (for testing only)

# 4. Build
dotnet build

# 5. Run
dotnet run --project NapasSwitch.Server
```

The server will display an interactive console:
```
```
+------------------------------------------------------------+
|                      Switch                                |
|                    Version 1.0                             |
+------------------------------------------------------------+

Press ENTER to start the server, or 'Q' to quit...
```

**Interactive commands** (when not in headless mode):
- **S** -- Show active connections
- **P** -- Pause / Resume the server
- **Q** -- Graceful shutdown

### Deploy to Linux / Azure VM

```bash
# 1. Publish the project
dotnet publish -c Release -o ./publish

# 2. Transfer the 'publish' folder and 'Config' folder to your VM

# 3. Install .NET 8.0 runtime on Ubuntu
sudo apt-get update && sudo apt-get install -y dotnet-sdk-8.0

# 4. Set environment variables (in ~/.bashrc for persistence)
export NAPAS_DB_CONNECTION_STRING='your-connection-string'
export ALLOW_HSM_STUB=true

# 5. Run
cd ~/napasswitch/publish
dotnet NapasSwitch.Server.dll --headless
```

### 6. Run as a Service (systemd)

To ensure the server runs 24/7 and restarts automatically on boot or after a crash, it is recommended to set it up as a systemd service.

1.  **Create the service file**:
    ```bash
    sudo nano /etc/systemd/system/napasswitch.service
    ```

2.  **Paste the following configuration** (adjust paths and user as needed):
    ```ini
    [Unit]
    Description="description"
    After=network.target

    [Service]
    User= <your_user>
    WorkingDirectory=/home/<your_user>/napasswitch/publish
    ExecStart=/usr/bin/dotnet /home/<your_user>/napasswitch/publish/NapasSwitch.Server.dll --headless
    Restart=always
    RestartSec=10

    # Environment Variables
    # IMPORTANT: Use double quotes around the assignment if the value contains semicolons
    Environment=NAPAS_DB_CONNECTION_STRING="your_connection_string_here"
    Environment=ALLOW_HSM_STUB=false (set to "true"for testing purposes)
    Environment=ASPNETCORE_ENVIRONMENT=Staging (or Production for production purposes)

    [Install]
    WantedBy=multi-user.target
    ```

3.  **Manage the service**:
    ```bash
    # Reload systemd to pick up changes
    sudo systemctl daemon-reload

    # Enable at boot and start now
    sudo systemctl enable napasswitch.service
    sudo systemctl start napasswitch.service

    # Check status
    sudo systemctl status napasswitch.service

    # Stop or Restart
    sudo systemctl stop napasswitch.service
    sudo systemctl restart napasswitch.service
    ```

4.  **View logs**:
    ```bash
    # View live scrolling logs
    sudo journalctl -u napasswitch.service -f

    # View previous 50 lines of logs
    sudo journalctl -u napasswitch.service -n 50
    ```

> **NOTE**: The `--headless` flag runs the server without interactive prompts, suitable for background execution. It also gracefully handles `SIGINT` (Ctrl+C) and `SIGTERM` for clean shutdown.

## Security

### PIN Block Translation

The switch translates PIN blocks (DE#52) between Acquirer and Issuer zone encryption keys to ensure each party can validate PINs encrypted under their own keys.

### HSM (Hardware Security Module)

The server is designed to integrate with real HSM devices (Thales payShield, Futurex, AWS CloudHSM) via the `IHsmProvider` interface:

```csharp
public interface IHsmProvider
{
    byte[] EncryptPinBlock(byte[] clearPinBlock, string zoneKey);
    byte[] DecryptPinBlock(byte[] encryptedPinBlock, string zoneKey);
    byte[] TranslatePinBlock(byte[] pinBlock, string sourceZoneKey, string destZoneKey);
    string EncryptPAN(string clearPAN);
    string DecryptPAN(string encryptedPAN);
}
```

For testing, a `SoftwareHsmStub` is provided (enabled via `ALLOW_HSM_STUB=true`). **This must never be used in production.**

### PAN Encryption

Card numbers (PAN) are encrypted before being stored in the database using the HSM provider. The `TransactionLog` table stores only encrypted PAN values.

### Connection String Security

Database connection strings must be provided via environment variables, not stored in XML config files. This follows PCI-DSS requirements for protecting sensitive credentials.
